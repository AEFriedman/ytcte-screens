## [2026-09-04] — SPEC review

`verdicts/open/` was empty apart from `.gitkeep`, so this is a first pass, not a resubmission. `proposed-fix/` is also empty, so I treated this as the spec review for v0.1.0.

Right thing to build: yes. A single static page with the published deck above a live clock strip solves the stated problem (clock on the same screen, nobody touching the display) without inventing infrastructure the Phase 0 brief ruled out. Deliberately living with the deck's letterboxing and the unverified orientation for this cycle is the correct call given nobody can look at the wall tonight, and the "one rotation on one wrapper" contingency plus the shipped viewport readout are the right shape for resolving it later.

**BLOCKER (implementation-and-safety issue, with a product decision inside it) — the Drive API key has nowhere safe to live.** The spec puts every screen-specific value, "the change-detection flag and key" included, in a single config block *in the page*, and that page lives in a public GitHub Pages repo. It then says enabling change detection is "a manual step outside this build and outside this repository." Those two statements cannot both hold: the only place the spec defines for the key is inside the repo. A browser-side Drive key is exposed to anyone viewing source in any case, but committing one to a public repo is the failure CLAUDE.md names explicitly, and the spec as written makes that the path of least resistance for whoever enables the feature later. Nothing unsafe ships this cycle (no key exists), which is why this is cheap to fix now and expensive to fix after someone pastes a key in. Which way it resolves — drop the Drive path from this cycle, or state where a key goes and what restrictions it must carry — is a product decision, not mine.

Non-blockers:
- The Drive change-detection path cannot be exercised at all this cycle (no Cloud project, no key), so it ships as a code path nobody can verify, and it is also the source of the blocker above. Worth considering deferring it entirely; the fixed timer is the thing that has to work tomorrow.
- The spec never says the secular and Hebrew dates roll over at midnight. Same silent-wrong-answer class the spec itself calls out for a frozen clock — a hallway display showing yesterday's date is wrong without anyone noticing. One sentence, and I'd expect the build to surface it, but naming it here so it isn't missed.
- No stated retry policy or backoff for the Hebcal lookup. "Keep the last good value" is specified; how hard it retries is not.
- The viewport readout ships enabled by default on a screen students and staff walk past. Fine and intentional, just noting it is visible to the public until the flag flips.

No code blocks, no function bodies, no file-and-line citations — the spec describes behavior, which is what it should do. Length and scope are right for one cycle.

Security review: not applicable — spec review. (The credential-placement concern above is recorded as a blocker, not as a completed security review.)
